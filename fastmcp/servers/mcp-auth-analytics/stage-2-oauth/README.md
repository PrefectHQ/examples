# Stage 2: OAuth with Keycloak

Part of the [MCP authentication example](../README.md): one FastMCP server over a synthetic analytics warehouse, secured in three stages. Each stage folder is a complete, runnable copy of the server.

| Folder | What changes | What it shows |
| --- | --- | --- |
| [`stage-1-api-key/`](../stage-1-api-key/) | One shared key (`StaticTokenVerifier`) | Every caller is the same identity, and everyone can `delete_user` |
| **[`stage-2-oauth/`](../stage-2-oauth/)** | Keycloak + `KeycloakAuthProvider` | Real per-user and per-service identity, still no limits |
| [`stage-3-authz/`](../stage-3-authz/) | Roles, scope, tool visibility, `audit.log` | Each caller sees a different server |

`tools.py` is identical in every stage, so `diff -ru stage-1-api-key/src stage-3-authz/src` (run from the example folder) shows only the security change.

## Run it

Needs [uv](https://docs.astral.sh/uv/) and Docker.

```bash
make up        # Keycloak on localhost:8080; returns once it is healthy
make stage2
make test      # no Keycloak needed
make down
```

`make stage2` reseeds the data, starts the server, runs `demos/stage2.py`, and stops the server. Logins are scripted. To use your browser instead, run `uv run python demos/stage2.py --interactive`.

Keycloak realm `analytics-demo` (`keycloak/realm-export.json`, generated by `keycloak/build_realm.py`):

| User | Password | Roles |
| --- | --- | --- |
| alice | alice | analyst |
| fran | fran | finance |
| adam | adam | admin, eu-data |
| `nightly-report-bot` (client credentials) | `nightly-report-bot-secret` | analyst |

These are demo credentials for a local container. Do not reuse them anywhere. The roles are already in the tokens, but nothing checks them until stage 3.

## What the demo shows

1. **Alice logs in:** her token carries her own subject ID and username, issued by Keycloak. The server holds no secrets; it only validates tokens.
2. **Adam logs in:** a different subject, so the server can tell people apart.
3. **A non-human caller:** `nightly-report-bot` uses the client credentials flow and gets a named identity of its own.
4. **Authenticated is not authorized:** Alice still sees all eight tools and can still `delete_user`.
5. **The log:** every line now names the caller, so at least you'd know it was Alice.

## Where to look

- `src/analytics_mcp/auth.py`: `KeycloakAuthProvider` pointed at the realm. `audience` rejects tokens issued for any other server, and `required_scopes` is what the server advertises in its 401 challenge.
- `demos/login.py`: the scripted Keycloak login used by the demos.
- `docker-compose.yml` and `keycloak/build_realm.py`: the realm, users and client policy.

## Client registration and Claude Code

The scripted demos register with Keycloak through Dynamic Client Registration (DCR), because a local script has no public URL. Claude Code uses Client ID Metadata Documents (CIMD): its client ID is the URL `https://claude.ai/oauth/claude-code-client-metadata`, which the current MCP spec prefers. Keycloak's CIMD support is experimental and needs 26.7 or later with `--features=cimd`; `docker-compose.yml` runs 26.8.2 with that flag. The full explanation is in the stage 3 README.

```bash
make cimd      # signs in as fran and alice with Claude Code's client ID URL
```

To connect Claude Code itself: with Keycloak up, run `make serve`, open Claude Code in this folder, and approve the `analytics` server from `.mcp.json`. Run `/mcp`, pick `analytics`, then **Authenticate**, and sign in as `fran` / `fran`. In this stage `whoami` shows the claude.ai client ID and Fran sees all eight tools.
