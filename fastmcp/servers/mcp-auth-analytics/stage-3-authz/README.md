# Stage 3: roles, scopes and an audit log

Part of the [MCP authentication example](../README.md): one FastMCP server over a synthetic analytics warehouse, secured in three stages. Each stage folder is a complete, runnable copy of the server.

| Folder | What changes | What it shows |
| --- | --- | --- |
| [`stage-1-api-key/`](../stage-1-api-key/) | One shared key (`StaticTokenVerifier`) | Every caller is the same identity, and everyone can `delete_user` |
| [`stage-2-oauth/`](../stage-2-oauth/) | Keycloak + `KeycloakAuthProvider` | Real per-user and per-service identity, still no limits |
| **[`stage-3-authz/`](../stage-3-authz/)** | Roles, scope, tool visibility, `audit.log` | Each caller sees a different server |

`tools.py` is identical in every stage, so `diff -ru stage-1-api-key/src stage-3-authz/src` (run from the example folder) shows only the security change.

## Run it

Needs [uv](https://docs.astral.sh/uv/) and Docker.

```bash
make up        # Keycloak on localhost:8080; returns once it is healthy
make stage3
make test      # no Keycloak or MotherDuck needed
make down
```

`make stage3` reseeds the data first (`delete_user` mutates it), starts the server, runs `demos/stage3.py`, and stops the server. Logins in the demo are scripted. To use your browser instead, run `uv run python demos/stage3.py --interactive`.

Keycloak realm `analytics-demo` (`keycloak/realm-export.json`, generated by `keycloak/build_realm.py`):

| User | Password | Roles |
| --- | --- | --- |
| alice | alice | analyst |
| fran | fran | finance |
| adam | adam | admin, eu-data |
| `nightly-report-bot` (client credentials) | `nightly-report-bot-secret` | analyst |

These are demo credentials for a local container. Do not reuse them anywhere.

## Stage 3 design notes

- **Two layers.** A server-wide `AuthMiddleware` requires the `analytics:read` scope on every request. Per-tool `auth=` checks read roles from Keycloak's `realm_access.roles`.
- **Scope plumbing.** The server advertises `analytics:read` in its 401 challenge, so clients request it. In the realm that one scope also carries `preferred_username`, `realm_access.roles` and the audience claim: Keycloak's dynamic client registration makes requested scopes optional, so a scope the client does not ask for adds nothing to its token. FastMCP also rejects tokens missing the scope at the transport, so `AuthMiddleware` is a second layer that also filters component lists.
- **Visibility.** A tool a caller may not use is absent from `tools/list`, and calling it by name fails as if it did not exist. No hand-written 403s.
- **`restrict_tag` not used.** It grants by scope, and the tool table is by role, so per-tool `auth=` reads cleaner here.
- **Custom check.** `get_metric(region="EU")` also needs the `eu-data` role (`EURegionGuard`). It depends on call arguments, which a role list cannot express.
- **Client registration.** See [Client registration: DCR and CIMD](#client-registration-dcr-and-cimd).

## Client registration: DCR and CIMD

An OAuth server only issues tokens to clients it knows. MCP clients and servers usually have never met, so the client has to introduce itself. This realm supports both ways the MCP spec allows:

- **Client ID Metadata Documents (CIMD)**, which the current MCP spec prefers. The client's ID is an HTTPS URL, and the document at that URL describes the client. Claude Code's is `https://claude.ai/oauth/claude-code-client-metadata`. Keycloak fetches it at sign-in, so nothing is registered ahead of time, and there is one client record per URL. Only URLs on trusted domains (`claude.ai` here) are accepted, and the user sees a consent screen naming the client.
- **Dynamic Client Registration (DCR)**, the fallback. The client posts its details and gets a new random client ID. The scripted demos use this, because a local script has no public URL to publish a document at. Every sign-in creates another client record, and the server cannot check who the client says it is.

Keycloak's CIMD support is experimental. It needs Keycloak 26.7 or later (26.6 does not advertise the `none` auth method, so Claude falls back to DCR; keycloak/keycloak#49730) and `--features=cimd`. `docker-compose.yml` runs 26.8.2 with that flag, and the realm has the client policy that trusts `claude.ai`.

One Keycloak detail matters for stage 3: CIMD clients get `fullScopeAllowed=false`, so a role only reaches their tokens if a scope they hold maps it. The realm maps all four roles onto `analytics:read`. Without that, fran signs in over CIMD and sees 2 tools instead of 5.

```bash
make cimd     # signs in as fran and alice with Claude Code's client ID URL
```

### Connecting Claude Code

`.mcp.json` registers this server for Claude Code. With Keycloak up, run `make serve`, then open Claude Code in this folder:

1. Approve the `analytics` server when asked.
2. Run `/mcp`, pick `analytics`, then **Authenticate**. Sign in as `fran` / `fran` and accept the consent screen.
3. Ask Claude to call `whoami`. `client_id` should be the claude.ai URL, which means Claude Code used CIMD. A random UUID means it fell back to DCR.

## Optional: MotherDuck

Local DuckDB is the default and nothing requires MotherDuck. Setting `ANALYTICS_DB=motherduck` adds a database-level layer: reads use a read scaling token, and only `delete_user` uses a short-lived read/write token. FastMCP decides who may call a tool, and the database token limits what the tool can do. `make stage3` ends with that second layer in either mode: a read connection is asked to `DELETE`, and the database refuses (DuckDB for a local `read_only=True` connection, MotherDuck for the read scaling token).

1. Create both tokens for a MotherDuck service account, not a personal one: a read scaling token and a read/write token with a `ttl`.
2. `cp .env.example .env` and fill in the two token variables and `ANALYTICS_DB=motherduck`. The Makefile loads `.env`; it is gitignored.
3. `make seed-motherduck` once. A read scaling token can only query a database that has been attached once with read/write access.

Things we hit:

- DuckDB is pinned to 1.5.6 because MotherDuck does not support 2.0 yet.
- The read scaling replica is eventually consistent, so a read right after `delete_user` can still show the old rows for a moment.
- DuckDB refuses two configs for one path, so the read and write connections use different `session_hint` values.

Locally the same split is enforced with `read_only=True` connections opened per call, because DuckDB will not hold read-only and read/write connections to one file at the same time. The tests run in local mode only.

Not included: FastMCP Gateway, TLS, secrets management, or anything production-grade.
